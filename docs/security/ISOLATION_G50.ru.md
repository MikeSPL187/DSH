# G-50. Изоляция Linux от приложения: исследование и варианты

Дата: 27.10.2026. Статус: исследование (решение по варианту — за владельцем).

## Что сейчас

- Host (Node, агент, плагины, MCP-серверы, `postinstall` проектов) работает под **proot** с тем же UID,
  что и DSH. proot — перевод путей через `ptrace`, а не граница прав: всё, что выполняется в Linux,
  имеет права приложения.
- Что из этого следует: код в Linux может прочитать файлы DSH (`/data/data/<пакет>/…`: база сессий,
  настройки, cookie Host, токен моста), ходить в сеть куда угодно и вызывать мост (токен лежит в
  `DSH_HOME` гостя — G-08 сделал мост fail-closed для **других приложений**, а не для кода внутри Linux).
- Что уже ограничено: ключ API хранится зашифрованным ключом Keystore (код в Linux видит шифротекст,
  но расшифровать ключ Keystore из другого процесса того же UID может — это не граница); опасные
  команды и удаление всегда спрашиваются; сторонние плагины из сети выключены по умолчанию (G-48);
  образ и плагин — только с хэшем из APK (G-41/G-42).

## Варианты

| # | Вариант | Граница прав | Цена | Вывод |
|---|---|---|---|---|
| 1 | `android:isolatedProcess` для Host | Да (отдельный UID) | У изолированного процесса нет сети и доступа к файлам приложения; rootfs и рабочую папку пришлось бы передавать дескрипторами, а Host нужна сеть (модели, npm, git). proot под ним не запускается. | **Не подходит** |
| 2 | Отдельное APK «DSH Runtime» (другой UID, своя подпись тем же ключом) | Да: песочница Android разделяет данные двух приложений | Второе приложение для установки; rootfs, Host и мост живут в нём; DSH общается с ним через связанный сервис/сокет с проверкой подписи; ключ API передаётся Host по запросу, а не лежит рядом с Linux. Перенос данных при обновлении. | **Рекомендую** как настоящую границу на всех телефонах |
| 3 | Сеть по разрешённому списку (провайдеры моделей, npm, PyPI, GitHub/GitLab, зеркала Debian) + переключатель «Полный доступ к сети» в проекте | Нет | Прокси в приложении и `HTTPS_PROXY`/`NO_PROXY` для Host. Обходится прямыми сокетами (proot не фильтрует сетевые системные вызовы, а seccomp не различает адреса) — защищает от случайных обращений и «честных» инструментов, не от злонамеренного кода. | Делать как **гигиену**, честно подписав в интерфейсе |
| 4 | Скрыть данные приложения от rootfs (не привязывать `/proc` хоста, свои `/data`) | Нет | Пути вне rootfs и так переводятся proot; но `/proc` нужен Node, а обход через `/proc/<pid>`, прямые системные вызовы без трассировки потомков или уязвимости proot возможен — тот же UID. | Полезно как ещё один слой, не граница |
| 5 | AVF / pKVM (настоящая VM, Microdroid или Linux) | Да (VM) | Разрешение `MANAGE_VIRTUAL_MACHINE` — только системным/привилегированным приложениям; обычному приложению из магазина VM недоступна (есть только на части Pixel/Android 15+ и для системных приложений). | **Следить**; режим «VM, где доступна» — когда Android откроет AVF сторонним приложениям |
| 6 | Режим «только чтение» по умолчанию для чужих проектов | Нет (политика агента) | Уже есть пресеты прав Host; можно ставить «только чтение» для клонированных репозиториев до явного разрешения. | Дешёвая мера против `postinstall` |

## Рекомендация

1. **Сейчас (дёшево):** варианты 3 и 6 — сеть по списку с переключателем «Полный доступ к сети» в проекте и
   «только чтение» для клонированных проектов; в интерфейсе прямо сказать, что это не граница.
2. **Следующий шаг (граница):** вариант 2 — Linux и Host в отдельном приложении «DSH Runtime» с другим UID.
   Тогда код в Linux не видит базу сессий, настройки и ключи DSH; мост и Host — только через проверенный канал.
3. **Потом:** вариант 5, когда AVF станет доступен обычным приложениям.

Варианты 2 и 3 меняют архитектуру и интерфейс — нужен выбор владельца, в этой работе они не реализованы.
